# SPEC — Data model and SQLite schema (step 2)

Status: APPROVED

## Context

The repository holds the step-1 findings document (`docs/opnsense-api-survey.md`,
pinned to OPNsense 26.7.3), the roadmap, two approved specs, and the
containerised toolchain: `Dockerfile`, `docker-compose.yml`, `ci/checks.sh`,
`.devcontainer/`, `.gitattributes`. A Go module exists — `go.mod` declares
`github.com/NaejEL/opnview`, `go 1.27.0` — with one package,
`internal/buildinfo`, created so the four project commands are not vacuous.
There is no storage package, no SQL file, no migration.

The development image carries `sqlite3` 3.46 and the `data` named volume is
mounted at `/data`, outside the bind-mounted working tree, because SQLite in WAL
mode on a Windows bind mount locks pathologically and because a `.db` /
`-wal` / `-shm` file must never land in the repository.

Everything the schema must carry is constrained by the step-1 findings rather
than by the roadmap's original assumptions:

- Suricata is an **alert source only**; `dns` events do not exist and `tls` /
  `http` events cannot be read back. There is no TLS/HTTP observation entity.
- The API flattens the nested alert object to the signature string, so severity
  and category are resolved through `get_rule_info/<sid>` and **cached**.
- Per-address-pair volume exists only at **daily** resolution for 62 days, and
  per-source totals at 300 s are kept **one hour**. The pre-computed aggregates
  are `opnview`'s **primary store**, not a cache over Insight.
- Every site-name attribution is **inferred** from resolver-lookup correlation.
  A provenance flag with one possible value states nothing, so the model carries
  the lookup the name came from and the delay to the flow instead.
- The `eve.json` cursor is a per-`file_id` byte-offset watermark over an
  alert-only feed, with rotation detection.
- Two join keys are first-class and runtime-discovered, each with a "not found"
  state: raw device name → interface description, and pf label / rule `uuid` →
  rule description.
- Source availability is a modelled state per source, because no source can be
  distinguished from silence by an empty result alone.
- Timestamps arrive as epoch seconds, ISO strings and year-less timezone-less
  syslog strings. Everything is stored as UTC epoch.

The roadmap's validation — "the schema answers all seven screens without
pathological queries" — is unenforceable as prose. This cycle delivers
**executable DDL** plus a per-screen query, and the Verifier executes them.

## Decisions taken with the maintainer

1. **Verification path.** A dedicated compose service `schema-checks`, granted
   as exactly one extra entry in the allowlist of `ci/factory.sh` and
   `ci/factory.ps1`. A schema failure stays distinguishable from a failure of
   the four Go commands, and the surface stays minimal. Not
   `docker compose run --rm dev *`.
2. **DDL form.** Numbered migrations under `migrations/` (`0001_*.sql`, …) with
   a `schema_version` table. Steps 4 to 7 will move the schema and step 8
   requires update without data loss; starting with no migration history would
   cost a conversion later.
3. **Aggregates.** Materialised tables, not views. A view over a growing base
   table cannot satisfy the query-plan criterion. Each aggregate row carries a
   freshness timestamp, and the refresh contract is written down for step 4 to
   honour.
4. **Blocked events** are a projection of flows — a view plus a partial index —
   not a separate table. Every blocked record comes from the same filter-log row
   as an allowed one with a different `action`; one ingestion path, no
   duplication.
5. **Device identity is a cascade**, most stable first: DHCP client identity
   (`client_id` / `duid` / `iaid`) when a lease provides it, then MAC, then
   address within its segment over time. The filter log carries no MAC at all,
   so a device seen only in flows must still be representable.
6. **Randomised MAC = the IEEE locally-administered bit**: second hex digit in
   `{2, 6, A, E}`. The requirement's literal wording ("second hex digit even")
   is wrong: it would additionally capture `0`, `4`, `8`, `C`, which are
   globally administered — real burned-in addresses — and mark genuine devices
   as unstable identities.
7. **Geo/ASN keyed per address**, carrying the MaxMind database build date so a
   stale lookup is visible, with a cache miss as a modelled state. MaxMind
   returns a prefix, but SQLite has no natural longest-prefix join.
8. **Tunnels carry their own attribute**, derived from the discovered
   `link_type` — never inferred from a name — so the UI can distinguish a tunnel
   from a VLAN.
9. **Default retention: 90 days**, stored as a seconds value, settable from a
   few hours to unlimited.
10. **Seed baseline: 100 000 rows** in the largest growing table, generated by a
    recursive CTE in pure SQL. No Go code, and no address literal committed:
    addresses are synthesised from counters at generation time.
11. **The seven queries live in an executable `.sql` file**, which is
    authoritative; `docs/data-model.md` references and explains them. A document
    and a file cannot drift if only one is executed.
12. **This cycle flips the step-2 row of the `ROADMAP.md` step table to `Done`**,
    as step 1's cycle did for its own row. That single-cell edit is the only
    change to the table.

## Scope

This cycle produces **no Go code**. The Go module stays exactly as it is.

### Files to create

1. **`migrations/0001_initial.sql`** (and further numbered files if the Builder
   judges a split clearer) — executable DDL covering the entities the roadmap
   names: segment (named zone, tunnels included), device, flow, blocked event
   (as the view of decision 4), DNS resolution, rule, domain attribution, alert,
   geo/ASN. Plus the supporting structures the survey forces: the
   interface-description map and the rule map, each with a "not found" state;
   the `get_rule_info/<sid>` severity and category cache; per-source
   availability state; the `eve.json` ingestion cursor; the four materialised
   aggregates; configuration (retention horizon, aggregate mode); and
   `schema_version`.

2. **`sql/queries/screens.sql`** — the seven representative queries, one per
   roadmap screen (Overview, Matrix, Segment, Device, Blocked, Alerts, Map),
   each labelled with its screen name and executable as written. Authoritative
   over the document.

3. **`sql/seed.sql`** — deterministic seed by recursive CTE, parameterised row
   count, no address literal, producing at least 100 000 rows in the largest
   growing table.

4. **`sql/schema-checks.sh`** (or equivalent name) — the harness: applies the
   migrations to a fresh database under `/data`, seeds it, runs the seven
   queries and their `EXPLAIN QUERY PLAN`, asserts the criteria below, and exits
   non-zero on any failure.

5. **`docs/data-model.md`** — per entity: what it represents, which survey
   section and which API fields feed it, its identity rule, its retention
   behaviour, its indexes. It cites the step-1 finding wherever the schema is
   shaped by one. It explains each of the seven queries and names, per query,
   the load-bearing index. It states the observation-point limit where it bears
   on volumes, and states that site names are inferred by resolver correlation
   with no second method available on 26.7.

### Files to modify

6. **`docker-compose.yml`** — add the `schema-checks` service, reusing the same
   base definition as `dev` and `checks`, with its command baked in so the host
   invocation is `docker compose run --rm schema-checks`, quoting-free and
   identical in both shells.

7. **`ci/factory.sh`** and **`ci/factory.ps1`** — grant exactly
   `Bash(docker compose run --rm schema-checks)` in addition to the existing
   checks entry. The two allowlist strings stay identical.

8. **`.vscode/tasks.json`** — add a task for the schema checks, `command` and
   `windows.command` identical or the override omitted.

9. **`ROADMAP.md`** — flip the step-2 status cell to `Done`. No other change.

## Project commands

The four project commands are **not** N/A: the module exists.
`docker compose run --rm checks` must exit `0` at the end of the cycle, with
`gofmt -l .` producing empty output and `go test ./...` still running the
`internal/buildinfo` test. The schema is verified separately by
`docker compose run --rm schema-checks`.

## Acceptance criteria

Every criterion is checked by executing a command in the container, except
those marked "inspection". Every database a check creates lives under `/data`.

**Executability and migrations**

- [ ] AC1 — Applying the migrations in order to a brand-new empty database
      exits `0` with nothing on stderr. Re-applying them is a no-op: the
      documented behaviour is the observed behaviour.
- [ ] AC2 — After applying, `PRAGMA integrity_check;` returns `ok` and
      `PRAGMA foreign_key_check;` returns no rows.
- [ ] AC3 — With `PRAGMA foreign_keys=ON;`, every declared foreign key
      resolves: inserting a child row whose parent does not exist fails, shown
      by a command exiting non-zero.
- [ ] AC4 — `schema_version` records the applied migrations, and its content
      after a fresh apply matches the files present in `migrations/`. A
      migration file with no corresponding row, or the reverse, fails.
- [ ] AC5 — Every entity named in *Scope* §1 exists in `sqlite_master`, as a
      table or — for blocked events only — as a view. The entity list in
      `docs/data-model.md` and the live `sqlite_master` listing are identical; a
      name in one and not the other fails.
- [ ] AC6 — There is **no** TLS/HTTP observation entity: no table or view whose
      name or documented purpose is a TLS or HTTP observation record.

**Seeded database and query plans**

- [ ] AC7 — The seed is deterministic: two runs produce identical row counts per
      table, and the largest growing table holds at least 100 000 rows. The row
      count is a parameter, not a literal scattered through the file.
- [ ] AC8 — `sql/queries/screens.sql` contains exactly seven queries, one per
      roadmap screen, each labelled with its screen name and executable as
      written.
- [ ] AC9 — Each of the seven queries, run against the seeded database, exits
      `0` and returns at least one row. A query returning zero rows fails: a
      plan over an empty result proves nothing.
- [ ] AC10 — For each of the seven, `EXPLAIN QUERY PLAN` shows **no** `SCAN` of
      any table `docs/data-model.md` lists as growing. `SCAN` of a table the
      document declares bounded (segments, rules, sources, settings) is
      permitted, and each bounded table carries its reason in the document. All
      seven plans are recorded verbatim.
- [ ] AC11 — Dropping an index the document names load-bearing for a given query
      turns that query's plan into a scan — demonstrated once on a throwaway
      copy of the seeded database, so the index is shown to be the reason the
      plan is good rather than a coincidence of data size.
- [ ] AC12 — The Matrix query returns, on at least one row, a byte volume, an
      allowed-connection count, a blocked-connection count and the matching
      rules, all four present and non-null.

**Model semantics**

- [ ] AC13 — East-west / north-south is answerable from stored data: a query
      classifies seeded flows from segment membership alone, with no literal
      address, CIDR, interface name or segment name in the query, the schema or
      its defaults.
- [ ] AC14 — Manual segment labelling is separate from discovery: updating a
      segment's user label leaves the discovered description unchanged and a
      query returns both. No column, default, trigger or check derives a
      segment's nature from its name (inspection plus a grep of the DDL for
      name-matching predicates).
- [ ] AC15 — Tunnels carry their own attribute, populated from the discovered
      `link_type` and not from any name. A query distinguishes a seeded tunnel
      segment from a seeded VLAN segment.
- [ ] AC16 — Device identity is the documented cascade: DHCP client identity,
      then MAC, then address within segment over time. Seeding the same physical
      device observed through a lease and through a flow yields one device; a
      device seen only in flows, with no MAC, is still representable and
      queryable. A seeded address reissued to another machine after a lease
      expiry does not merge the two.
- [ ] AC17 — Randomised MAC uses the IEEE locally-administered bit: a MAC whose
      second hex digit is in `{2, 6, A, E}` is marked an unstable identity, and
      one whose second hex digit is in `{0, 4, 8, C}` is **not**. Both
      directions are asserted. Two randomised observations with different MACs
      remain two rows, never merged into one phantom device.
- [ ] AC18 — Site-name attribution: an attribution row cannot exist without the
      resolver lookup it came from (foreign key, demonstrated by a failing
      insert) and carries the delay between that lookup and the flow as a
      stored, queryable value. There is **no** provenance or method column — its
      absence is asserted against the column list, and the document states why.
- [ ] AC19 — A flow with no attribution is representable: the Device query
      returns it with address, country and operator and a null site name, rather
      than omitting it. The per-device attribution rate is computable by a query
      the document gives, and that query is executed.
- [ ] AC20 — Alerts: a seeded alert joins to a device and a segment and returns
      signature, severity, source, destination and timestamp in one query.
      Severity comes from the `get_rule_info/<sid>` cache, not from the alert
      row.
- [ ] AC21 — The rule-info cache models a miss distinctly: a seeded alert whose
      `sid` has no cache entry still returns from the Alerts query with an
      explicit unknown-severity state, not a dropped row.
- [ ] AC22 — Unknown rule and unknown interface: a seeded blocked event whose
      `rid` matches no known rule is returned by the Blocked query with an
      explicit unknown-rule state; likewise a flow whose raw interface name is
      absent from the interface map. Present, not missing.
- [ ] AC23 — Source availability: each of the five sources holds exactly one of
      reachable / present-but-disabled / unavailable, with a timestamp and the
      probe that determined it. An invalid state value is rejected by a
      constraint (failing insert), and one query returns the current state of
      all five.
- [ ] AC24 — `eve.json` cursor: the watermark is unique per `(file_id, byte
      offset)` — a duplicate insert fails — and replaying the same simulated
      ingestion twice leaves the alert count unchanged. Rotation is
      representable and a query returns that state.
- [ ] AC25 — NetFlow de-duplication is explicit: the schema makes the key that
      collapses direction-doubled per-pair records unambiguous, and the document
      states it, citing the survey gap. Seeding a direction-doubled pair yields
      one logical volume, not two.
- [ ] AC26 — Timestamps: every column storing an instant is an integer UTC
      epoch. A query over `pragma_table_info` for every table returns no
      instant-carrying column declared `TEXT`, and a constraint rejects an
      out-of-range value. The document maps each of the three input shapes to
      the normalised column, citing the survey.

**Aggregates, retention and purge**

- [ ] AC27 — The four aggregates (1 h / 24 h / 7 d / 30 d) are materialised
      tables, populated from `opnview`'s own stored observations rather than
      from any column assuming Insight supplies sub-daily per-pair data. A query
      returns a non-empty result for each period, and the document cites survey
      data source 3 for why.
- [ ] AC28 — Each aggregate row carries a freshness timestamp, and
      `docs/data-model.md` states the refresh contract step 4 must honour —
      when a period is recomputed, and how a stale row is recognised.
- [ ] AC29 — Aggregate mode: the document names one query answering "volumes,
      segments, countries, operators" that reads **no** table containing domain
      names. The query is executed, returns rows, and a check of its referenced
      tables confirms the domain-carrying tables are absent from it.
- [ ] AC30 — Retention is configuration, not a constant: the horizon is stored
      in the database, defaults to 90 days expressed in seconds, is settable to
      a value of hours and to unlimited, and no retention duration appears as a
      literal in any query or index (inspection).
- [ ] AC31 — Purge works: with a finite horizon, the documented purge removes
      seeded rows older than the horizon from every growing table and removes
      none newer; with unlimited it removes nothing. Both directions asserted by
      row counts before and after.
- [ ] AC32 — Purge leaves the model consistent: afterwards
      `PRAGMA foreign_key_check;` returns no rows and the aggregates remain
      queryable for the periods the document says survive a purge.
- [ ] AC33 — Geo/ASN: keyed per address, carrying the MaxMind database build
      date, with a cache miss as a modelled state returned by a query rather
      than an absent row.

**Zero hardcoded configuration, and hygiene**

- [ ] AC34 — No interface name, VLAN name, segment name, CIDR or IP address
      appears as a literal in the migrations, their defaults, constraints or
      indexes, in the seven queries, or in the seed file. Checked by a grep for
      dotted-quad and CIDR patterns over every file this cycle adds, returning
      no match outside values synthesised from counters at generation time.
- [ ] AC35 — No assumed segment count, address-family layout or interface count:
      the schema and the seven queries run correctly against a seed generated
      with a different number of segments and devices, the counts supplied at
      check time.
- [ ] AC36 — Every table or column fed by an OPNsense source carries, in
      `docs/data-model.md`, the endpoint and API field it comes from, with the
      citation URL already present in `docs/opnsense-api-survey.md`. A column
      claiming a source the survey does not document fails. The document also
      states, per source, that an unavailable source is recorded as an
      availability state rather than rendered as an absence of data.
- [ ] AC37 — `docs/data-model.md` states the observation-point limit where it
      bears on volume figures, and states that site names are inferred by
      resolver correlation with no alternative method on 26.7.
- [ ] AC38 — `docker compose run --rm schema-checks` exits `0` and is the single
      invocation covering every executable criterion above. The same string
      works from PowerShell and from bash; both exit codes recorded and equal.
- [ ] AC39 — The allowlists of `ci/factory.sh` and `ci/factory.ps1` grant
      exactly the two invocations `docker compose run --rm checks` and
      `docker compose run --rm schema-checks`, and nothing wider. The two
      strings are identical between the files.
- [ ] AC40 — `docker compose run --rm checks` still exits `0`: `gofmt -l .`
      empty, `go vet ./...`, `go build ./...`, `go test ./...` each `0`, with at
      least one test actually running.
- [ ] AC41 — `shellcheck` reports no error-level finding on the harness script,
      `bash -n` exits `0`, and every `*.sh` and `*.sql` file is LF-terminated in
      the working tree.
- [ ] AC42 — Everything added is in English; no French word in any file this
      cycle touches.
- [ ] AC43 — `git status --porcelain` lists only the files this spec creates,
      the modified `docker-compose.yml`, `ci/factory.sh`, `ci/factory.ps1`,
      `.vscode/tasks.json` and `ROADMAP.md`, and this spec file. No `*.db`,
      `*.db-wal`, `*.db-shm`, no scratch file, no `factory-logs/` entry.
- [ ] AC44 — The `ROADMAP.md` step-2 status cell reads `Done`; the table still
      has eight rows, numbered 1 to 8, with the same titles and deliverables,
      and no other line of `ROADMAP.md` changes.
- [ ] AC45 — Every database created by a check lives under `/data`; the
      bind-mounted working tree contains no database file after the checks run.

## Out of scope

- Any Go code: no storage package, no migration runner, no `database/sql`, no
  SQLite driver choice, no `cmd/` tree.
- Any OPNsense API call, collector, scheduler, credential or setup wizard —
  step 4.
- Any HTTP endpoint, payload shape, template, asset or screen — steps 5 to 7.
- The static HTML mockup — step 3.
- MaxMind download, refresh and licence handling: the geo/ASN entity is
  modelled, the acquisition is step 4.
- Performance tuning beyond "the seven queries use an index": no benchmark
  target, no `ANALYZE` strategy, no page-size or cache tuning mandated.
- `README.md`, `ct/install.sh`, packaging — step 8.
- Any live OPNsense instance.

## Risks

- **Query plans are data-dependent.** SQLite will scan a small table regardless
  of indexes, so an under-seeded database hides a missing index. The 100 000-row
  baseline and AC11 bound this, but the figure is a judgement call.
- **Designing aggregates before the collector exists.** Their shape is fixed
  before any real ingestion rate is known; a wrong granularity costs a migration
  at step 4 or 5. Mitigated by decision 2 — migrations exist from the start.
- **Device identity has no real data behind it yet.** The cascade is a
  modelling decision; getting it wrong produces duplicate devices or merged
  phantoms, and the randomised-MAC rule makes the failure asymmetric.
- **NetFlow per-pair records are direction-doubled and port-approximated.**
  AC25 forces the de-duplication key to be explicit, or step 4 will
  double-count volumes.
- **Unverified survey claims.** The survey carries `UNVERIFIED:` markers on the
  ISC lease contract, the resolver log-line grammar and the volume estimates.
  Columns resting on those are provisional and the document must say so.
- **The blocked-event view interacts with the entity list.** Decision 4 makes it
  a view rather than a table; AC5 accepts that explicitly, but any future code
  expecting a table will need the document to be unambiguous.
- **Widening the allowlist a second time.** `schema-checks` is a second granted
  invocation. It is narrow and its command is baked into the compose file, but
  it is still a widening and is acknowledged as one.
- **CRLF.** A `.sql` or `.sh` file checked out with CRLF fails inside the
  container with a confusing error. `.gitattributes` exists; AC41 guards it.
